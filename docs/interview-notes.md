# Interview notes

Answers grounded in what this repository actually does, with the file to open if someone
wants to see it.

---

### "Why do you need an agent? Why not Power BI?"

Power BI is excellent at visualising known metrics on predefined dashboards. This sits on the
**investigation layer above** it. A dashboard can only answer questions someone anticipated
when they built it; a manager's real question — *why did this move, and what should I do* —
requires deciding at run time which datasets, cuts, statistical methods and business context
are relevant. That decision is the product. I see this as a conversational investigation and
decision-support layer on top of BI, not a replacement for it.

Concretely: the dashboard view in this app already shows revenue down and North weak. It
cannot tell you the fill rate was 49% because of a customs hold on one supplier, or price the
fix — that took eight further queries chosen based on what the previous ones returned.

---

### "Why an LLM? You could just write those SQL queries."

The hard part is not one query, it is **which query comes next**. If revenue is down, do you
look at regions, products, channels, customers or inventory? The answer depends on what the
last query returned. That branching is what the LLM does here.

Everything else is deliberately not the LLM's job: SQL generation for the standard cuts is
parameterised code, the arithmetic is pandas, and the conclusion comes from an explicit
scorer. I also shipped a deterministic planner that encodes the same policy — so I can show
the value the model adds (flexible, open-ended questions) separately from the value it does
not need to add (the numbers).

`app/agents/planner.py`

---

### "How do you prevent hallucination?"

Four layers.

1. **The model cannot produce a number.** Tools return `summary`, `data` and `facts`; the
   summaries are generated by the tools themselves, in Python. The narration prompt says to
   use only the supplied figures, and the deterministic fallback narrator proves the report
   is complete without any model at all.
2. **Conclusions come from a scorer, not a paragraph.** Six hypotheses, each with a readable
   scoring function over collected facts, each returning evidence with its source table.
   `app/agents/scoring.py`
3. **Guardrails on data access.** Validator plus read-only connection plus allow-listed
   filters. `app/agents/sql_tool.py`, `backend/tests/test_guardrails.py`
4. **Evaluation with an independent oracle.** The eval suite recomputes the headline movement
   with a separately written SQL query and fails the case if the agent's figure differs by
   more than 0.05 points. `app/eval/runner.py`

### "Is it autonomous?"

Semi-autonomous, deliberately. It plans and executes an investigation without help — it
chose fourteen steps in that run, and a different question produces a different three. But
every recommendation with financial or operational consequence carries
`approval_required: true` and is presented for a human decision. Business analytics has to
stay auditable and supervised; an agent that silently raised purchase orders would be a worse
product, not a better one.

---

### "How do you know the root cause is right, rather than a correlation?"

Two things, and I keep them separate in the output.

The **mechanism** is measured, not inferred: `inventory.units_lost` records demand that stock
could not serve. A 49% fill rate is not "sales correlated with low stock" — it is a direct
record of orders that could not be filled. That is the one link where I claim causation.

Everything else is reported as **evidence**, ranked, with alternatives explicitly ruled out
and the ruled-out ones still shown. The scores are labelled strength of evidence, not
probability of causation — I would only use causal language after a proper design
(difference-in-differences against unaffected regions, or a synthetic control). Confidence is
capped at 0.92 and the reasons behind the number are printed, including that the quantified
impact only covers 35% of the total movement.

### "What happens when the model is wrong or unavailable?"

- Provider error mid-run → the deterministic planner takes over, the run completes, the UI
  shows the switch and the reason.
- A repeated tool call → refused by the planner, no loops.
- A tool exception → captured as a warning finding; the investigation continues.
- No key at all → the whole system runs offline, which is how the current eval numbers were
  produced.

### "How would this scale to real data?"

- **Database**: it is SQLAlchemy Core with portable SQL and no dialect-specific date
  functions, so PostgreSQL is an env-var change (`docker compose up -d`). At warehouse scale
  the same tools point at BigQuery/Snowflake; the per-tool SQL is already aggregate-only.
- **Latency**: the current run is ~4 s because every tool is an indexed aggregate. Adding an
  LLM planner adds one round trip per step, which is why the tools are coarse-grained — each
  one answers a whole analytical question rather than fetching rows.
- **Governance**: read-only role, row caps, allow-listed filters, and a full audit trail —
  every run records the tools, arguments and figures that produced the conclusion.
- **Semantics**: the metric definitions live in one module and in a written reporting
  standard, which is what stops two answers to the same question.

### "What is the ML doing? Isn't it decoration?"

It narrows the search space before any reasoning happens. Twenty-four products, one month —
several will be down by chance. The scan scores each entity against **its own** twelve-month
history with a robust z-score (median/MAD, so one spiky month does not set the scale) and
adds IsolationForest for multivariate outliers. The purifier comes out at z = -3.5 against
noise elsewhere at ±1.

Honest caveat I would volunteer: IsolationForest on five regions is meaningless, so it is
skipped below eight entities and the method string says which detector actually ran.
`app/analytics/anomaly.py`

The second ML piece is the what-if: a Monte-Carlo inventory simulation bootstrapping the
product's own daily demand and the supplier's own lead-time distribution, priced against
holding cost. That is what turns "raise safety stock" into "net ₹78K per 90 days".

---

### "Where does RAG fit? Everyone bolts one on."

Only where documents are genuinely the source of truth: **policy**. The thresholds in the
recommendations — 15% of lead-time demand for Class A, alert at 7 days of cover, escalate
above a 5-day average delay — are retrieved from the policy corpus and cited, not invented by
the model. Numbers live in the warehouse; rules live in documents; the agent uses each for
what it is. Retrieval is TF-IDF because the corpus is a few dozen chunks and I wanted it
deterministic and offline; FAISS with embeddings is a change behind one function.

### "You built auth into a POC — why, and how?"

Because a BI tool without access control is not a product, and the panel will ask. It also
forced a real design question: the investigation streams over server-sent events, and
`EventSource` cannot send an `Authorization` header — so the session had to be a cookie.
It is httpOnly and SameSite=Lax, which also removes the XSS-token-theft path; a bearer token
is still accepted for scripted clients.

Passwords use scrypt from the standard library — memory-hard, no native build step, and the
parameters live in the hash string so they can be raised later without invalidating anyone.
Sign-up validates format and rejects common passwords; repeated failures hit a per-IP,
per-email window that returns 429 with a wait; wrong-password and unknown-account responses
are indistinguishable, and a hash verification runs either way so the timing matches.

Two things I would call out as POC-grade rather than production-grade: the lockout counter is
in-process (Redis in a real deployment), and there is no email verification or password
reset. Accounts sit in their own MetaData so regenerating the synthetic dataset — which drops
every analytics table — cannot delete users.

`backend/app/auth/`, `backend/tests/test_auth.py` (20 tests)

### "What would you do next?"

1. **Causal validation** — difference-in-differences against unaffected regions before using
   the word "cause" anywhere in the UI.
2. **Memory** — recurring root causes across months ("this supplier has caused three of the
   last six incidents").
3. **Proactive monitoring** — invert it: the agent watches the fill-rate and lead-time
   signals and opens the investigation itself, since both moved before revenue did.
4. **LLM-judge evaluation** of narrative quality on top of the current structural checks, and
   LangSmith tracing for step-level latency and cost.
5. **Write-back with approval** — draft the purchase-order escalation email for a human to
   send.
