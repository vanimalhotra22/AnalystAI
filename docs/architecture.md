# Architecture

## 1. The shape of the problem

A dashboard answers *what happened*. Answering *why* is a search problem: there are dozens of
dimensions, most movements are noise, and the explanation usually lives in a different table
from the symptom. A human analyst handles that with a policy — measure, localise, test supply
before demand, walk upstream, rule out the obvious alternatives, quantify.

InsightPilot encodes that policy as an agent loop with typed tools, and keeps every number
outside the language model.

## 2. Data layer

### Schema

```
        purchase_orders ─────────► suppliers
               │                       │
               ▼                       ▼
   ┌────────► inventory ◄─────────  products  ◄─────── marketing
   │            (daily)                 │
   │                                    │
regions ◄──────────── sales ────────────┘
   ▲                    │
   └──── customers ─────┴──── channels
```

Nine tables. The one that makes root-cause analysis possible is `inventory`, because it
records `units_lost` — demand that stock could not serve. Without it, a supply failure and a
demand collapse look identical in `sales`.

### Why the generator simulates rather than samples

`backend/app/data/generate.py` runs a day-by-day simulation:

```
demand(product, region, day) = base × seasonality × weekday × trend × marketing_lift × noise
units_sold  = min(demand, stock_on_hand)
units_lost  = demand − units_sold
stock       = stock − units_sold + arrivals_today
if stock ≤ reorder_point and no open PO:  raise PO, arrival = order_date + supplier lead time
```

Because sales are the *served* portion of demand, a late consignment mechanically produces a
stockout, unserved demand, a product decline, a regional decline and a company decline — a
chain the agent can rediscover from the tables alone.

The planted July 2026 storyline:

| layer | event | visible in |
|---|---|---|
| primary | AirTech (SUP03) consignments due 30 Jun – 17 Jul held; northern hub released 18 Jul | `purchase_orders.delay_days` |
| effect | SmartAir Purifier 3000i at zero stock in North for 17 days | `inventory.stockout`, `units_lost` |
| secondary | North marketing cut ~32%, air-care cut a further ~30% | `marketing.spend` |
| noise | mild unexplained softness in East | `sales` |
| decoys | pricing, discounting, customer mix, other suppliers — all stable | `sales`, `customers` |

Everything is seeded (`SEED=20260824`), so the demo is byte-for-byte reproducible.

## 3. Analytics layer — the deterministic core

`app/analytics/`

| module | responsibility |
|---|---|
| `periods.py` | resolves "this month", "June 2026", "Q2 2026", "2026-07 versus 2026-06" against the data's own calendar, and carries the resolved range into every result |
| `metrics.py` | revenue summary, breakdowns with contribution-to-change, trends, inventory health, supplier performance, marketing, pricing, customers |
| `anomaly.py` | robust z-score (median/MAD) + IsolationForest over each entity's own 12-month history; `demand_vs_served` for the supply-vs-demand test |
| `impact.py` | rupee impact from unserved units × realised price; Monte-Carlo safety-stock what-if |

Two decisions worth defending in review:

**Period length is never assumed.** July has 31 days, June 30 — a 3.3% mechanical uplift.
Every comparison reports both the total change (-5.49%) and the per-day rate (-8.54%), and
the reporting standard in `docs/policies/` says the per-day rate is the like-for-like figure.

**Contribution is measured in currency, not percentage.** A tiny line swinging 300% must not
outrank the product that actually moved the money.

**SQL is portable and parameterised.** No dialect-specific date functions (grouping happens
in pandas), every filter comes from a fixed allow-list and binds as a parameter, so the same
code runs on SQLite and PostgreSQL and cannot be steered by user text.

## 4. Agent layer

### Tool contract

Fourteen tools (`app/agents/tools.py`). Each returns:

```python
{
  "summary": "P103/NORTH: demand 79 units, 39 served, 40 unserved - fill rate 49.4% ...",
  "data":    {...},   # structured; the charts and the report render from this
  "facts":   {"fill_rate_pct": 49.4, "unserved_units": 40, "supply_side": True},
}
```

`summary` is generated by the tool, not the model — so the live feed is trustworthy even
without an LLM. `facts` is the flat scalar namespace the hypothesis scorer reads; the model
never writes into it.

| group | tools |
|---|---|
| measure | `get_revenue_summary`, `get_breakdown`, `get_trend` |
| localise | `detect_anomalies` |
| supply | `check_demand_vs_served`, `get_inventory_health`, `get_supplier_performance` |
| demand / commercial | `get_marketing_performance`, `check_pricing`, `get_customer_metrics` |
| decide | `quantify_impact`, `simulate_safety_stock`, `search_policy` |
| escape hatch | `run_sql` (validated, read-only, row-capped) |

### The graph

```
START → understand → investigate ──(planner returns a step)──► investigate
                          │
                          └──(planner returns None / budget spent)──► validate
                                                                        │
                                                        conclude ◄──────┘
                                                            │
                                                        narrate → END
```

`investigate` performs exactly **one** tool call per visit and loops through a conditional
edge, so investigation length is decided at run time. State accumulates through reducers
(`findings` append, `facts` merge), which makes the run its own audit trail.

### Planning

`LLMPlanner` gives the model the question, the findings so far and the tool schemas, and asks
for one tool call or `finish_investigation`. Duplicate calls are refused. On any provider
error the run continues under `HeuristicPlanner` and the UI shows the switch.

`HeuristicPlanner` is an ordered list of guarded steps — genuinely branching, not a script:
it only measures the stockout if the fill rate came back below 97%, only walks up to
suppliers if there was a stockout, and only quantifies impact if units were actually lost.

### Evidence and conclusions

`app/agents/scoring.py` holds one scoring function per hypothesis, each returning a status
(`supported` / `partial` / `ruled_out` / `untested`), a 0–1 strength score, and evidence
lines with their source table. `causal_chain()` then assembles the mechanism, including only
links that have a measured number behind them. `overall_confidence()` combines the strongest
hypothesis, how many alternatives were dismissed, and how much of the movement the quantified
impact actually covers — capped at 0.92, because one month of evidence never justifies
near-certainty. The reasons are returned alongside the number and shown in the UI.

### Narration

The model receives validated figures and writes at most four paragraphs, under instructions
never to introduce or recompute a number. Without a key, a template narrator produces the
same content from the same facts. The UI labels which one wrote it.

## 5. Accounts and the guard

`app/auth/` is three small modules:

| file | responsibility |
|---|---|
| `models.py` | the `users` table, in **its own MetaData** so the data generator's `drop_all` cannot take accounts with it |
| `security.py` | scrypt hashing, constant-time verification, sign-up validation, JWT issue/decode, and an in-process failure window for brute-force damping |
| `service.py` | account storage, authentication, the demo account, and `current_user` — the FastAPI dependency every analytics route depends on |

Choices worth defending:

- **scrypt from the standard library** rather than bcrypt: memory-hard, no native build step
  on any platform, and one less dependency to justify. Parameters are stored in the hash
  string (`scrypt$n$r$p$salt$hash`) so they can be raised later without invalidating anyone.
- **The session is an httpOnly cookie.** Page scripts cannot read it, which removes the
  XSS-token-theft path — and, specifically for this app, `EventSource` cannot set an
  `Authorization` header, so a cookie is the only way the investigation stream can
  authenticate at all. A bearer header is still accepted for scripted clients.
- **Credentialed CORS lists its origins.** A wildcard origin is illegal with credentials, so
  the dev origins are enumerated.
- **Failures are indistinguishable.** Wrong password and unknown account return the same
  message, and a hash verification runs either way so the timing is similar.
- **Lockout is in-process**, which is honest for a single-node POC; a real deployment moves
  that counter to Redis so it survives restarts and spans replicas.

The routing side: `/`, `/login` and `/signup` are public; `/app` is wrapped in a
`RequireAuth` route that remembers where the visitor was heading and returns them there
after sign-in. A 401 arriving mid-session (an expired token in a tab left open) clears the
user and drops back to the sign-in page rather than showing a broken workspace.

## 6. API and UI

All analytics routes depend on `current_user`; `/api/health` stays public for probes.

- `POST /api/auth/signup|login|demo|logout`, `GET /api/auth/me` — session lifecycle.
- `POST /api/investigate` — synchronous, returns the whole report (used by the eval harness).
- `GET /api/investigate/stream` — server-sent events; one event per agent action.
- `GET /api/dashboard` — headline KPIs, trend, regional contribution, availability alerts, so
  the UI has something to show before anyone asks a question.
- `POST /api/sql` — the guarded query endpoint, refusals included.

The investigation runs in a worker thread and pushes events into a queue that the SSE
endpoint drains, so a long run streams instead of blocking. Two SSE details that bite in
practice and are handled here: `error` is reserved by `EventSource` for transport failures
(a failed run is streamed as `run_error`), and the client must close the stream on `done`, or
the browser reconnects and silently re-runs the whole investigation.

The front end is a small React Router app: a landing page that explains the product and
replays a real investigation trace, a combined sign-in/sign-up page (with the one-click demo
account), and the guarded workspace. The workspace is three panes — ask, live investigation,
business insight — plus charts driven straight off `report.charts`: revenue trend, contribution bars, the inventory ledger with
stockout bands shaded, the anomaly scatter, the delayed-consignment table and the what-if
card.

## 7. Extension points

| want to | change |
|---|---|
| add a data source | one function in `analytics/`, one `Tool` in `agents/tools.py` |
| add SSO / OAuth | `auth/routes.py` issues the session; the rest of the app only sees `current_user` |
| add a hypothesis | one scoring function in `agents/scoring.py` |
| swap the vector store | `agents/knowledge.py::search` (TF-IDF → FAISS/embeddings) |
| swap the LLM | `agents/llm.py` (Anthropic, OpenAI and Gemini adapters ship) |
| move to Postgres | `DATABASE_URL` + `READONLY_DATABASE_URL`; no code changes |
| add tracing | LangSmith env vars — LangGraph emits spans already |
